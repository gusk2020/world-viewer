`tools/search_climate_seaice.mjs` を、10,000試行級の本探索を始める**直前**に
監査した記録。目的は一つ:

> 「この探索は、これまで何度も起きた退化解・採点の抜け穴へまた逃げないか」

気候モデル本体・UI・表示・Teacherデータは**一切変更していない**
(`git diff --stat` で `tools/search_climate_seaice.mjs` の1ファイルのみ)。
本探索は実行していない。

安全復元点: **`safe-v0.8-sea-ice-balance`**(commit `552bb04`、監査直前の状態)。

## 1. 監査した逃げ道と、その測定結果

すべて `pareto-balanced` 相当(既知良好、Teacher A 54.43 / Teacher B 19.32 /
陸氷 62.7 / 海氷 53.3 / 季節性 17.0 / 経度構造 27.4%)を基準に、
1パラメーターずつ動かして実測した。

| 逃げ道 | Teacher A | 季節性 | 経度構造 | 陸氷面積 | 旧constraint |
| --- | --- | --- | --- | --- | --- |
| 基準(既知良好) | 54.43 | 17.0 | 27.4% | 2.74% | 通過 |
| **1. 偽融点の復活** `snowBalanceWeight=0.2, snowSummerMeltC=+6` | **55.01** | 17.0 | 27.4% | 3.31% | **通過** |
| **2. ITCZ無力化** `range=60, smooth=60`(引きは30のまま) | **56.37** | **1.2** | **22.2%** | 2.74% | **通過** |
| **3. 季節性0** `s=15, itcz=15`(空間の下限) | 50.71 | **0.0** | 21.7% | 6.30% | **通過** |
| **4a. 陸融解0** `snowMeltDegreeDay=0` | 37.43 | 17.0 | 27.4% | **11.00%** | **通過** |
| **4b. 海融解0** `seaIceMeltDegreeDay=0` | 47.43 | 17.0 | 27.4% | 2.74% | **通過** |

### 逃げ道1が最も重い ——「却下した設計」が探索の最良解になる

`classifyPoint` の陸雪氷は

```
out[SNOW] = 旧閾値 + (年間収支 - 旧閾値) * snowBalanceWeight
```

という**混合**である。`snowBalanceWeight` の探索下限が 0.2 なので、判定の
最大8割は依然として**旧方式の暖季閾値**が握る。そしてその閾値の中心
`freezeTemperatureC + snowSummerMeltC` は、`snowSummerMeltC` が [-30, +15] で
探索対象だったため**任意の値に置ける**。

つまり探索は、雪氷収支ラウンドが明示的に却下した
**「融点 +6 °C」という非物理な埋め合わせを、そのまま再構成できた**。
しかも測定上それは基準点を**両目的で上回る**(A 54.43→55.01、陸氷 62.7→65.2、
Teacher B は完全に同一)。10,000試行の探索は初期にこれを見つけ、前線の
高Teacher A側をこれで埋めたはずである。

これは「旧方式との都合のよい混合でEarthだけへ過適合できないか」という
監査項目そのものであり、**答えは「できた」**。

### 逃げ道2は「headline knob は正しいのに機構が死んでいる」型

`itczLandPullDeg` を探索空間の上限 30 に置いたまま、
`itczPullRangeDeg=60`(引きの窓が半球全体に広がる)と
`itczSmoothDeg=60`(経度方向に強く平滑化)を同時に効かせると、
経度依存の変位はならされて消える。

結果、**引きの数値は 30 と読めるのに、季節性クラスは 17.0 → 1.2、
経度構造は 27.4% → 22.2%** ——旧zonalモデル(19%)のすぐ上まで戻る。
それでいて Teacher A は 54.43 → **56.37** と大きく上がる。

**パラメーターの下限だけを見張っても、機構は下流で無力化できる。**
これが今回の監査で最も重要な一般教訓である。

### 逃げ道3は小規模探索が実際に produce 済み

前回の2000試行探索の前線20件のうち、上位14件は**季節性クラスが厳密に 0.0、
経度構造 19.7〜20.6%** ——すなわち旧zonalモデルと同じである。
すでに起きていたことであり、仮定ではない。

### 逃げ道4は「面積下限では原理的に捕まらない」

面積制約は**下限のみ**だった。融解率を0にすると陸氷面積は教師 3.33% に対し
**11.00%**、陸氷 IoU は 27.3% ——「場所が間違っている大量の氷」である。
下限だけでは検出できない。ユーザーの問い
「面積下限だけで場所が間違っている大量の氷を防げるか」への答えは **No**。

## 2. Pareto目的をどうするか —— A / B / C の判断

**採用: B(2目的を維持し、消滅防止の緩い hard constraint だけ追加)。**

- **Cを採らない理由**: 季節性・経度構造・地域・各クラスを目的に格上げすると
  4〜8目的になり、10,000試行では前線が発散して収束しない。さらに悪いことに、
  それらを**最大化**すると「Köppenだけを最大化するhack」に直結する。
  これらは**得点化してはいけない**量である。
- **Aを採らない理由**: 上の測定が示すとおり、2目的だけでは退化解が
  前線を占拠する。Teacher A と Teacher B は逃げ道2を**罰しない**
  (A は上がり、B は 19.32→17.73 と 1.6 しか下がらないので非劣に残る)。
- **Bが正しい理由**: 必要なのは「その機構が生きているか死んでいるか」の
  二値判定であって、順位づけではない。constraint は探索を教師へ引っ張る力を
  持たず、崖から落ちるのを止めるだけである。

## 3. 修正後の hard constraint(すべて outcome ベース)

パラメーター値ではなく**結果**を見る。逃げ道2〜4はいずれもパラメーターを
空間の内側に保ったまま下流で機構を殺すため、パラメーター下限では捕まらない。

| 制約 | 値 | 導出 |
| --- | --- | --- |
| 陸氷 面積 | 0.3%〜10% | 教師 3.33% の約1/10〜約3倍 |
| 陸氷 IoU | ≥ 20% | 達成値 62.7〜71% の約1/3 |
| 海氷 面積 | 0.1%〜3.0% | 教師 1.01% の約1/10〜約3倍 |
| 海氷 IoU | ≥ 15% | 達成値 52.7〜53.7% の約1/3 |
| 季節性クラス合計 | ≥ 2% | zonalモデルは厳密に 0.0、実在する季節構造は 4.8 以上。**空いている谷間**に置いた |
| 経度構造シェア | ≥ 24% | zonal 19%、「ITCZが実際に効いている」実測域 24.5〜27.4% の下端 |

数値はすべて**小規模探索と既存成功候補の実測から**取った。厳しさの確認:

| | 判定 |
| --- | --- |
| 既知良好 `pareto-balanced` 相当 | **通過** |
| 既知良好 `seaice-pareto-teacher-b` | **通過** |
| 逃げ道2 ITCZ無力化 | **棄却**(季節性/経度構造) |
| 逃げ道3 季節性0 | **棄却**(季節性/経度構造) |
| 逃げ道4a 陸融解0 | **棄却**(陸氷面積) |
| 逃げ道4b 海融解0 | **棄却**(海氷面積) |

逃げ道1は constraint ではなく**探索空間側**で閉じた(次節)。

**教師への過適合になっていないか**: `lon` はモデル自身の湿潤度場から計算する
量で、教師を一切参照しない。季節性クラスは Teacher B 由来だが、目的 b が
17% に達する量に対して**下限 2%** であり、「季節気候をどこにも描かない」
という**モデルの能力の欠落**だけを弾く。地域別補正・Earth固有座標・
Teacher画像からの逆算は一切入れていない。

**これらの制約が何ではないか**: 任意の惑星が満たすべき物理法則ではない。
すべての数値は今回の実行の Earth 教師データ(その氷面積、その
Köppen由来の季節クラス)に対して較正された、**この較正探索専用の
ガードレール**であり、`js/climate.js` が実行時に強制する制約でも、
架空の惑星が満たすべき条件でもない。Earthよりはるかに氷が多い/少ない
世界や、経度方向の構造が実質無い世界は、それ自体は正当な気候でありうる
——ただし「このモデルの何のパラメーターがEarthと一致するか」という
今回の探索の問いに対する答えとしては不適格、というだけである。

## 4. 探索空間の修正 —— `snowSummerMeltC` を [-30, +15] → [-30, 0]

永久雪氷の融点が**氷点より上**にあるのは物理的に成立しない。上限を実物理の
氷点(`freezeTemperatureC` = 0 °C)に置くことで、逃げ道1は探索が
**提案すらできなくなる**。

既知良好候補はすべて -23〜-25 に位置するので、失うものはない。
上限 0 での再測定(`w=0.2, snowSummerMeltC=0`)は Teacher A **54.18** ——
基準の 54.43 を**下回る**ので、前線を占拠することもない。

**削除はしていない**。パラメーターは schema にそのまま残り、探索範囲だけを
物理的に正しい側へ狭めた。

## 6. 停止条件の監査 —— patience は事実上「発火しない」設計だった

**旧実装**: 前線に何かが追加されたら `sinceImprovement = 0`。

2目的の連続空間では、前線は曲線であり、既存点の周りを少し揺らせば
**ほぼ常に非劣な点が生まれる**。したがって patience は永久にリセットされ、
「500試行改善なし」は**実質的に一度も成立しない**。実行は必ず試行上限か
時間上限で終わる ——ユーザーの懸念(「frontのごく小さい入れ替わりだけで
patienceが無限にリセットされないか」)は**そのとおりだった**。

**修正**: 前線の**ハイパーボリューム**(原点基準、両目的とも IoU なので
0 以下にならず参照点として妥当)が相対 1e-4 を超えて増えたときだけ
改善とみなす。前線が内部で入れ替わっているだけでは進捗と数えない。

**もう一つの修正**: patience は **constraint を通過した試行だけ**を数える。
修正後の constraint では棄却率が高い(実測: cold start で 71〜100%、
warm start で 39%)ため、全試行を数えると「500試行」が実質150試行になり、
**何も見つける前に shard が止まる**危険があった。試行上限と時間上限は
そのまま効くので、全部棄却され続ける実行も無限には走らない。

**前線の上限**も入れた。旧実装では前線は無制限に増え、10,000試行では
数百件になりうる。jitter の親を前線から一様に選ぶため、前線が膨らむほど
凡庸な内部点を親にする確率が上がる。NSGA-II 標準の crowding distance で
`--keep`(既定 40)まで間引く。**両端の点は決して落とさない**
——落とすと報告されるトレードオフの幅が黙って縮む。

## 7. ウォームスタートが無い —— smoke test が見つけた最大の実務的欠陥

修正後の constraint で **seed 7 / 100試行が 100件すべて棄却**され、前線は
空のままだった。12次元を一様サンプリングして8つの outcome 制約を同時に
満たす確率はおよそ **1/200**。誤起動した実行(次節)でも、最初の前線メンバーが
出たのは **218試行目**だった。

Stage 7 はこれとほぼ同じ失敗を記録している ——
「4 shard × 200試行で改善ゼロ」——そして同じ方法で直した:
**すでに機能する答えの近くから始め、探索用にランダムサンプリングも残す**。

**修正**: 起動時に、その世界自身の
`worlds/<world>/sea-ice-candidates.json`(この作業ライン自身が commit した
Pareto候補)を読み、constraint を満たすものを前線の初期メンバーにする。
何も発明していない。制約を満たさない項目(出荷既定、修正前ベースライン)は
黙って飛ばす。`--seedFrom` で差し替え可能、ファイルが無ければ cold start。
`--resume` した実行には**再投入しない**。

効果(実測):

| | cold start | warm start |
| --- | --- | --- |
| 80試行後の前線 | 0 件 | **2 件** |
| 棄却率 | 100% | **39%** |
| 最良 Teacher A | —— | **55.41**(seed の 55.27 を更新) |

## 8. その他の修正

- **`resolveClimateSets(config).sets[0]` → `defaultId` で取得。**
  世界が2つ目の気候セットを持った瞬間、探索が**間違ったベース**から
  最適化を始める潜在バグだった。
- **shard の RNG を独立させる warm-up。**
  `seed*2654435761 + shard*40503` は異なる**値**を与えるが、xorshift32 の
  周期上で近い位置に落ちない保証はない。各 shard が探索開始前に
  `1013*(shard+1)` 回空回しする。確率的な懸念を計算で消す方が安い。
- **checkpoint に `constraints` と `space` を保存。**
  将来その前線を読む人が、どのガードの下で得られた結果かを判断できる。

## 9. shard 設計と推奨

- **推奨 shard 数: 4**(1コア1shard、既存ラウンドと同じ)。
- **1 shard あたり 10,000 試行**、`--hours 6` は安全網として維持。
  実測 **約0.2秒/試行**なので、10,000試行は **1 shard あたり約35〜40分**、
  4 shard 並列で**全体40分程度**。時間上限は実際には効かない。
- **patience 500**(constraint 通過試行のみを数える、上記の修正込み)。
- **注意点**: warm start により4 shard は同じ初期候補から始まるため、
  出発点は相関する。RNG が独立なので早期に分岐するが、探索の多様性を
  重視するなら **1〜2 shard を `--seedFrom` に存在しないパスを与えて
  cold start** にするとよい。ただし cold shard は最初の数百試行を
  実行可能領域の探索に費やす。

推奨コマンド(**この監査では実行していない**):

```
for s in 0 1 2 3; do
  node tools/search_climate_seaice.mjs worlds/kasoku-sekai \
    --shard $s --trials 10000 --hours 6 --patience 500 --seed 9001 \
    --out runs/seaice-shard$s.json &
done; wait
node tools/search_climate_seaice.mjs --merge runs/seaice-shard*.json --keep 40
```

最終候補は `--step 1` で再採点すること(探索は `--step 2`。既知の差は
0.03ポイント)。

## 11. 事故の記録

監査中、`node -e "import('./tools/search_climate_seaice.mjs')"` で
schema を読もうとしたところ、**モジュールの `main()` が走り、既定引数の
探索が起動した**。約2分後に気づいて `kill -9` し、生成された
`search-seaice-shard0.json` は削除した。**進んだのは 576 試行**で、
成果物は一切残していない。

正直に記録する理由は二つある。ひとつは「10,000回級の探索は実行禁止」という
指示に対し、意図せず576試行を走らせたこと自体を報告すべきだから。
もうひとつは、これが**再発しうる設計上の罠**だから ——
このファイルは import しただけで探索が始まる。将来 schema や定数を
読みたいときは、**import せずに読む**か、引数付きで CLI として呼ぶこと。

副産物として、修正後 constraint 下の棄却率 71% と 1試行あたり約0.2秒という
実測値がここから得られた(§9 の見積もりの根拠)。

## 12. 最終判定

### READY

- 実測で確認された退化解 4系統のうち、3系統は outcome constraint が棄却し、
  1系統(偽融点の再構成)は探索空間から締め出した。
- 既知良好候補はすべて通過する ——ガードは崖を塞いだだけで、
